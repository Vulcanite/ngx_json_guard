# Engine comparison: structural validation

Four engines were run against the same corpus on the same host, each in
its own container constrained to 2 vCPU / 4 GiB (NGINX 1.26.2,
libmodsecurity 3.0.13, Coraza 3.7.0 via Caddy 2.11.3; run of 2026-08-24,
commit `08851ee`).

The comparison that matters here is **JSON structural validation only** —
no CRS, no signatures, no SQLi/XSS rules. Three processor-only profiles:

| Profile | What it measures |
|---|---|
| **JSON Guard** | NGINX + `ngx_json_guard` |
| **ModSecurity JSON only** | NGINX + libmodsecurity JSON body processor, rules off |
| **Coraza JSON only** | Caddy + Coraza JSON body processor, rules off |

## How long structural validation takes

Client-observed HTTP latency on the mixed 1–100 MiB JSON processor
corpus, 4 workers. No CRS. Lower p50 / p95 means the engine finished
sooner; higher MiB/s means it moved more JSON in the same wall time.

| Engine | p50 | p95 | MiB/s | Peak RAM |
|---|---:|---:|---:|---:|
| JSON Guard | **414 ms** | **2579 ms** | **167.2** | **363 MiB** |
| ModSecurity JSON only | 593 ms | 6526 ms | 74.8 | 1654 MiB |
| Coraza JSON only | 822 ms | 7894 ms | 55.7 | 2148 MiB |

Read the medians carefully:

- These are **not** parser-only timers. Upload, proxy, and a tiny
  upstream are in every number. Only JSON Guard publishes
  `$json_guard_inspection_us`; this page does not invent an equivalent
  for ModSecurity or Coraza.
- Guard's p50 is helped by **early 400/413** on malformed and over-limit
  bodies in this mixed corpus. Baseline (no JSON validation) was 127.2
  MiB/s / 639 ms p50 — it has to proxy every byte.
- Coraza runs on **Caddy**; Guard and ModSecurity run on **NGINX**. Same
  body corpus and cgroup budget, not the same proxy.

On a **fixed 20 MiB body**, the published per-case medians are Guard vs
ModSecurity only (Coraza had no per-case 20 MiB median in this run):

| Case | JSON Guard | ModSecurity JSON only | Guard + ModSecurity |
|---|---:|---:|---:|
| Clean 20 MiB, accepted | 476 ms | 696 ms | 829 ms |
| Malformed tail 20 MiB, rejected | 395 ms | 542 ms | **323 ms** |
| High-cardinality 20 MiB, accepted | 294 ms | 515 ms | 519 ms |

## Who rejects which structural class

Every cell is what the *proxy* did. "Pass" means the body was forwarded;
the test upstream also parses JSON, so some forwarded bodies were
eventually rejected by the *application*.

| Violation class | Baseline | JSON Guard | ModSecurity | Coraza |
|---|---|---|---|---|
| Malformed syntax (trailing comma, bad brackets) | pass | **400** | **400** | **400** |
| Invalid escape / invalid number | pass | **400** | **400** | **400** |
| Invalid UTF-8 in strings | pass | **400** | **400** | pass |
| Unpaired UTF-16 surrogate (`"\ud800"`) | pass | **400** | pass | pass |
| Trailing garbage after document | pass | **400** | **400** | **400** |
| Nesting depth &gt; 100 | pass | **413** | 400† | 400† |
| Array/object width &gt; 10,000 | pass | **413** | **413** | **413** |
| Key length &gt; 4096 | pass | **413** | pass | pass |
| Number length &gt; 256 | pass | **413** | pass | pass |
| String length &gt; 64 MiB | pass | **413** | pass | pass |
| Total tokens &gt; 100,000 | pass | **413** | pass | pass |
| **Classes caught at the edge (of 11)** | **0** | **11** | **7** | **6** |

† ModSecurity's and Coraza's depth/width rejections come from *their own
fixed internal parser limits*, which you cannot configure. The guard's
thresholds are directives in `nginx.conf`.

Three takeaways:

1. **Everyone catches plain syntax errors.** If malformed JSON were the
   only concern, any JSON-aware engine would do.
2. **Only the guard has configurable structural limits.** Depth, key,
   number, string, token and width limits are nginx directives.
3. **The guard is the only engine rejecting unpaired surrogates.**
   libmodsecurity and Coraza both tolerate them. Coraza also forwards
   invalid UTF-8 (the 400 in that row comes from the upstream app).

## Full CRS is a different measurement

Under full CRS 4.25.0 with 20 MiB bodies, adding the guard in front of
ModSecurity does not change CRS throughput (1.77 vs 1.80 MiB/s — noise).
A single 64 MiB string under full CRS: **268 s with Coraza vs 46.6 s with
ModSecurity** — both dominated by *rule evaluation*, which is exactly
what the processor-only charts above exclude.

The complete methodology is in `BENCHMARK.md`. Headline processor numbers
are also on [Performance](/docs/performance/results).
